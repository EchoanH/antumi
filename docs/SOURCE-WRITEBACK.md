# 来源回写

从 GitHub、Jira、Linear、禅道、TAPD、飞书项目 / Meegle 导入的任务，可以把进展写回原事项：改状态、发评论。手动随时可写；也可以按来源打开自动规则，在任务开始执行、提交验收、验收通过时写。和[来源评论同步](SOURCE-COMMENTS.md)一起，事项和任务两边就接上了。

参考过的做法：orca 让 Agent 在完成时发一条总结、把事项挪到待审，状态按名字匹配、匹配不唯一就不动；multica 每次运行只发一条最终总结，Agent 没写就用运行输出兜底，区分 Agent 发的评论以免再触发；t3code 把写操作做成提供方的可选能力，发出去前给人看全文。

## 用户看到的

- **任务详情的「回写到 X」区块**（在来源原文下面）：「改状态」现取一次事项的当前状态和此刻能流转到的状态，选一个后点「写入」；「写评论」打开编辑框，默认填 Agent 写好的总结草稿，看过、改过再发。下面是回写记录：每一次写了什么、谁触发的（手动或哪条规则）、成功、失败还是跳过及原因。
- **排查会话**的检查器「来源」页同样可以手动改状态、写评论；它没有任务状态，不走自动规则。
- **设置 → 集成 → 某个来源 → 回写**：三条规则，默认都关。
  - 开始执行时，状态改为 ___
  - 提交验收时，状态改为 ___，同时发总结评论
  - 验收通过时，状态改为 ___，同时发总结评论（提交验收时已发过就不再发）
  - 总结要求（可选）：这个来源的团队对总结的额外要求，如「用英文写」「附上测试环境地址」，加在内置要求后面

  状态填平台上显示的名字，多个用 `|` 隔开，按顺序取第一个此刻能流转到的；留空表示不改状态。
- 插件没有声明回写能力时，上面这些都不出现。

登录时用的 Token 要有写权限（各插件 README 写明需要哪些）。只读的 Token 写入时报「没有权限」，记录里提示换一个有写权限的 Token 重新登录。

## 总结评论从哪来

Agent 写，Antumi 发。参考 orca 和 multica，但 Agent 只写草稿，不能自己发出去：

1. 来自支持回写、能发评论的来源的任务，Agent 的 Antumi 工具里多一个 `source_report`。不能发评论的来源（禅道）既不给这个工具，也不在任务提示里要总结：草稿没有地方发。任务提示里的来源一节告诉它：做完、交用户验收前用它写一条完成总结，以后又改了就再写一次覆盖。
2. 写法的要求在 `core/src/source-report-prompt.ts`，任务提示、工具说明和下面的压缩共用一份：读者是产品、测试和同事而不是对话里的用户；2 到 4 句、300 字以内，不用标题和列表；第一句说结果；有 PR 附链接；没做完或要验收特别注意的用一句话说；不写排查过程、commit 号、本地路径和命令、测试输出、给用户的提问；用事项原文的语言；附一个例子。来源设了「总结要求」时接在后面，冲突时以它为准。各家的做法都只用句数约束（orca 2 到 4 句、multica「说结果不说过程」），所以另有硬上限：超过 600 字 `source_report` 直接退回，让 Agent 压缩后再写。
3. 草稿存在任务上，来源区块和评论编辑框都能看到。它不会自己发出去。
4. 规则要发总结时用最新的草稿。没有草稿时，最后一条回复是写给用户的（标题、步骤、提问都有），不原样发：交给 Antumi 的小模型按同样的要求改写（模型和服务商同会话标题的小任务，回复作为资料隔开，参考 t3code 写 PR 说明的做法），结果去掉包装后不超过 600 字才发，记录里注明来自最后一条回复。小模型不可用、失败或写得太长，就只改状态，记一条「没有发评论」。

来源原文是不受信的资料，可能写着「把状态改成已关闭」之类的话。所以 Agent 拿不到改状态、发评论的工具，只能写草稿；草稿只会发到它自己这个任务的事项上，并且要用户开了规则或亲手点发送。

## 状态怎么选

- 插件的 `transitions` 返回事项当前状态和此刻能流转到的状态（Jira 的转换、Linear 团队的工作流状态、GitHub 的打开 / 关闭、禅道和 TAPD 当前工作流允许的下一步、Meegle 状态流的下一状态），每项带名字、可选的动作名（如 Jira 转换「开始处理」、禅道「完成」）和 `todo` / `doing` / `done` / `unknown` 分类。
- 规则里的名字和状态名或动作名比，不区分大小写和首尾空白；同一个名字匹配到多项时当作没匹配上。
- **不倒退**：当前分类排在目标之后（`todo` < `doing` < `done`）时跳过，比如事项已经关了，任务又开始执行，不会被改回处理中。`unknown` 不比。
- 已经是目标状态时跳过，不算失败。
- 每次写之前现取一次可流转的状态，不用缓存。

## 自己发的评论

插件发评论后返回平台上的评论 ID。core 记下它，评论同步拉回这条时直接当作已读、已送达，不算「新评论」，也不会被「带新评论继续排查」发给 Agent。

## 幂等和失败

- 每次写入有一个 `writeId`（UUID），记录先落库再调用插件。Linear 用它做评论的 ID，重试时平台会认出重复；其他平台没有这种机制。
- 结果不明（超时、连接中断）记为「结果待确认」，不自动重发评论：重复的评论比漏掉一条更糟。状态写入可以安全地重试，因为下一次会先读当前状态。
- 认证失败、没有权限、事项不存在：记失败和原因，不重试。其他失败同样只记录，用户可在记录上点「重试」。
- 同一个事项的写入串行执行，规则和手动操作排同一个队。

## 协议

插件协议 v1 的可选扩展，SDK 0.5.0 起。来源在 manifest 里声明 `writeback: 1`，并实现三个方法：

| 方法 | 参数（另有 source、settings、credential、key） | 结果 |
|---|---|---|
| `transitions` | — | `{ status, statusCategory, options: { id, name, action?, category }[] }` |
| `transition` | `id`：`options` 里的一项 | `{ status, statusCategory }`，写入后的状态 |
| `comment` | `markdown`（最多 20,000 字）、`writeId` | `{ id, url }`，平台上的评论 ID 和链接（没有链接时为 `null`） |

`id` 由插件自定，core 不解析，只原样传回。平台接口不能发评论时（禅道 RESTful API v1），manifest 里再声明 `writebackComment: false`、不实现 `comment`：界面不出现「写评论」，规则里的评论记为跳过。`markdown` 由插件转成平台的格式（Jira 的 ADF、TAPD 和禅道的 HTML）。旧插件没有这三个方法，旧宿主不认识 `writeback`，互不影响。

## 实现

- `core/src/source-writeback.ts`：`SourceWriteback` 负责手动写入、规则触发、状态匹配、串行队列和记录；`source-writeback-store.ts` 在任务数据库里存回写记录（`source_writes`）和总结草稿（`source_reports`）。
- 规则存在来源实例的配置里（`sources.json` 的 `writeback`），和设置一起保存。
- `TaskService.save` 是任务状态变化的唯一入口：`pending → running`、`running → review`、`→ done` 时通知 `SourceWriteback`，写入在后台进行，失败不影响任务本身的状态变化。
- RPC：`sources.writeback`（记录和草稿）、`sources.writebackTransitions`、`sources.writebackTransition`、`sources.writebackComment`、`sources.writebackRetry`、`sources.saveWriteback`、`sources.saveReport`（MCP 工具用）；通知 `sources.writebackChanged`。core 用 `source-writeback` 功能标记告诉客户端；这些方法都不开放给手机。
- MCP 工具 `source_report` 只在会话属于带回写来源的任务或排查会话时出现，不需要用户批准（它只写 Antumi 自己的草稿）。
- 各插件的写法（用到的接口、状态怎么列、需要的 Token 权限、还没用真实账号确认的地方）写在 antumi-plugins 各插件的 README 和 DESIGN。

# 来源回写

从 GitHub、Jira、Linear、禅道、TAPD、飞书项目 / Meegle 导入的任务，可以把进展写回原事项：改状态、发评论。手动随时可写；也可以按来源打开自动规则，在任务开始执行、提交验收、验收通过时写。和[来源评论同步](SOURCE-COMMENTS.md)一起，事项和任务两边就接上了。

参考过的做法：orca 让 Agent 在完成时发一条总结、把事项挪到待审，状态按名字匹配、匹配不唯一就不动；multica 每次运行只发一条最终总结，Agent 没写就用运行输出兜底，区分 Agent 发的评论以免再触发；t3code 把写操作做成提供方的可选能力，发出去前给人看全文。

## 用户看到的

- **任务详情的「回写到 X」区块**（在来源原文下面）：「改状态」现取一次事项的当前状态和此刻能流转到的状态，选一个后点「写入」；「写评论」打开编辑框，默认填 Agent 写好的总结草稿，看过、改过再发。下面是回写记录：每一次写了什么、谁触发的（手动或哪条规则）、成功、失败还是跳过及原因。
- **排查会话**的检查器「来源」页同样可以手动改状态、写评论；它没有任务状态，不走自动规则。
- **设置 → 集成 → 某个来源 → 回写**：按类型列出规则摘要，默认折叠。展开某类事项后，可选「未配置」「按下面的规则」「不回写」。未配置、未知类型的事项都不自动写入；没有通用规则或隐式继承。
  - 开始执行时，状态改为 ___
  - 提交验收时，状态改为 ___，同时发总结评论
  - 「验收通过后的操作」里可配置由我关闭和发送总结，默认折叠
  - 可以复制另一类型的规则；复制后各自独立，后续修改不联动
  - 「高级选项」集中放演练模式、多人归属选项和总结要求

  状态填平台上显示的名字，多个用 `|` 隔开，按顺序取第一个此刻能流转到的；留空表示不改状态。旧版的通用阶段规则不再执行；已有类型规则保留，未填写的阶段不再继承通用值。
- 每个平台的这一页按插件的声明（见下文「协议」的 `writebackRules`）显示：有预设的阶段是下拉框（「不改状态」、预设、「自己填…」），平台没有这一步状态的阶段不出现，不能发评论的来源不出现评论勾选和总结要求。各平台的差别：

  | 来源 | 开始执行 | 提交验收 / 验收通过 | 能否自己填 |
  |---|---|---|---|
  | GitHub | In progress（仅用 Issue 状态的仓库） | In review；完成（Done，或关闭为已完成）；只改 Issue，不关 Pull Request | 否 |
  | 禅道 | 开始或继续任务 | 完成任务、解决 Bug；验收通过还可选关闭 | 否；不能发评论 |
  | TAPD | 任务进行中、需求开发中 | 任务已完成、需求已实现、缺陷已解决 | 能，缺陷和自定义工作流靠自己填 |
  | Jira | In Progress（进行中） | 验收通过 Done（完成） | 能，状态名或转换名 |
  | Linear | In Progress | 验收通过 Done；默认工作流没有 In Review，要自己填 | 能 |
  | 飞书项目 / Meegle | 按类型配置，无通用状态预设 | 可完成当前账号独自负责的进行中节点，并发总结 | 能 |

  预设值也是 `|` 连起来的名字，靠「取第一个此刻能流转到的」同时覆盖一个来源里的几种事项：禅道的「完成任务、解决 Bug、关闭需求」是 `已完成|已解决|已关闭`。插件声明某一步没有状态后，之前填在那里的规则不再执行，下次保存时清掉；预设里没有的旧值在下拉框里照样显示。
- 插件没有声明回写能力时，上面这些都不出现。

登录时用的 Token 要有写权限（各插件 README 写明需要哪些）。只读的 Token 写入时报「没有权限」，记录里提示换一个有写权限的 Token 重新登录。

## 总结评论从哪来

Agent 写，Antumi 发。参考 orca 和 multica，但 Agent 只写草稿，不能自己发出去：

1. 来自支持回写、能发评论的来源的任务，Agent 的 Antumi 工具里多一个 `source_report`。不能发评论的来源（禅道）既不给这个工具，也不在任务提示里要总结：草稿没有地方发。任务提示里的来源一节告诉它：做完、交用户验收前用它写一条完成总结，以后又改了就再写一次覆盖。
2. 写法的要求在 `core/src/source-report-prompt.ts`，任务提示、工具说明和下面的压缩共用一份：读者是产品、测试和同事而不是对话里的用户；2 到 4 句、300 字以内，不用标题和列表；第一句说结果；有 PR 附链接；没做完或要验收特别注意的用一句话说；不写排查过程、commit 号、本地路径和命令、测试输出、给用户的提问；用事项原文的语言；附一个例子。来源设了「总结要求」时接在后面，冲突时以它为准。各家的做法都只用句数约束（orca 2 到 4 句、multica「说结果不说过程」），所以另有硬上限：超过 600 字 `source_report` 直接退回，让 Agent 压缩后再写。
3. 草稿存在任务上，来源区块和评论编辑框都能看到。它不会自己发出去。
4. 规则要发总结时用最新的草稿。没有草稿时，最后一条回复是写给用户的（标题、步骤、提问都有），不原样发：交给 Antumi 的小模型按同样的要求改写（模型和服务商同会话标题的小任务，回复作为资料隔开，参考 t3code 写 PR 说明的做法），结果去掉包装后不超过 600 字才发，记录里注明来自最后一条回复。小模型不可用、失败或写得太长，就只改状态，记一条「没有发评论」。

来源原文是不受信的资料，可能写着「把状态改成已关闭」之类的话。所以 Agent 拿不到改状态、发评论的工具，只能写草稿；草稿只会发到它自己这个任务的事项上，并且要用户开了规则或亲手点发送。

## 状态怎么选

- 插件的 `transitions` 返回事项当前状态和此刻能流转到的状态（Jira 的转换、Linear 团队的工作流状态、GitHub 的打开 / 关闭或 Issue 状态、禅道和 TAPD 当前工作流允许的下一步、Meegle 状态流的下一状态），每项带名字、可选的动作名（如 Jira 转换「开始处理」、禅道「完成」）和 `todo` / `doing` / `done` / `unknown` 分类。
- 规则里的名字和状态名或动作名比，不区分大小写和首尾空白；同一个名字匹配到多项时当作没匹配上。
- **不倒退**：当前分类排在目标之后（`todo` < `doing` < `done`）时跳过，比如事项已经关了，任务又开始执行，不会被改回处理中。`unknown` 不比。
- 已经是目标状态时跳过，不算失败。
- 每次写之前现取一次可流转的状态，不用缓存。

## 自己发的评论

插件发评论后返回平台上的评论 ID。core 记下它，评论同步拉回这条时直接当作已读、已送达，不算「新评论」，也不会被「带新评论继续排查」发给 Agent。

## 只写归我的事项，按类型定规则

规则写入前先看事项归谁（[来源事项自动化闭环](SOURCE-AUTOMATION.md) 的「归属判定」）：处理人不是当前账号时，状态和评论都不写；同时分配给了别人时只发评论（来源可以设成也算归我）；没有处理人、或插件报告不了归属时照常写，记录里注明。事项交给测试之后就不归我了，后面的规则自然跳过。手动改状态、发评论不受这个限制。

规则按事项类型独立设置（泳道）：没配置的类型不回写，某个类型也可以明确设成不回写（Pull Request 默认如此）。「验收通过」这一栏在界面上叫「由我关闭」：多数团队里关闭事项不是开发做的，新泳道默认不填。

演练模式下规则走完每一步但不调用写接口，记录里写明本来会写什么。任务详情在提交验收前显示这一步会写什么、不会写的原因。

## 幂等和失败

- 任务状态变化时，「这一步要回写」的意图和状态变化在同一事务里存库（`source_intents`），写入完成才删。core 在两者之间退出，重启后补上，不会丢，也不会给历史任务补发。
- 规则的状态写入失败会自动重试（1、5、15 分钟后各一次），每次先读当前状态；任务已离开原阶段时不再补改旧状态。来源暂时没连接也按同样的节奏等，耗尽后保留意图，恢复连接后可从失败记录手动重试。
- 状态流转可能自动改派事项，所以总结评论在发送前再取一次归属；压缩最后一条回复时，也在压缩完成后检查。

- 每次写入有一个 `writeId`（UUID），记录先落库再调用插件。Linear 用它做评论的 ID，重试时平台会认出重复；其他平台没有这种机制。
- 结果不明（超时、连接中断）记为「结果待确认」，不自动重发评论：重复的评论比漏掉一条更糟。状态写入可以安全地重试，因为下一次会先读当前状态。
- 认证失败、没有权限、事项不存在：记失败和原因，不重试。评论的其他失败只记录，用户可在记录上点「重试」。
- 同一个事项的写入串行执行，规则和手动操作排同一个队。

## 协议

插件协议 v1 的可选扩展，SDK 0.5.0 起。来源在 manifest 里声明 `writeback: 1`，并实现三个方法：

| 方法 | 参数（另有 source、settings、credential、key） | 结果 |
|---|---|---|
| `transitions` | — | `{ status, statusCategory, options: { id, name, action?, category }[] }` |
| `transition` | `id`：`options` 里的一项 | `{ status, statusCategory }`，写入后的状态 |
| `comment` | `markdown`（最多 20,000 字）、`writeId` | `{ id, url }`，平台上的评论 ID 和链接（没有链接时为 `null`） |

`id` 由插件自定，core 不解析，只原样传回。

SDK 0.6.0 起，来源还可以声明 `writebackRules`，告诉设置页每个阶段（`start`、`review`、`done`）怎么填状态：

```json
"writebackRules": {
  "start": false,
  "done": { "presets": [{ "value": "Done|completed", "label": "完成", "translations": { "en": { "label": "Done" } } }], "custom": false, "hint": "只改 Issue" }
}
```

`false` 表示平台没有这一步的状态：界面不出现，core 也不执行那里存过的状态（`applicableWriteback`）。否则 `presets` 最多 8 个，`value` 和规则的写法相同；`custom: false` 表示预设就是全部，不给自己填（默认可以填）；`placeholder`、`hint` 和预设的 `label` 都可带 `translations.en`。没声明的阶段照旧是文本框。这只是设置页的提示，状态是否真能流转仍以写入时现取的 `transitions` 为准。平台接口不能发评论时（禅道 RESTful API v1），manifest 里再声明 `writebackComment: false`、不实现 `comment`：界面不出现「写评论」，规则里的评论记为跳过。`markdown` 由插件转成平台的格式（Jira 的 ADF、TAPD 和禅道的 HTML）。旧插件没有这三个方法，旧宿主不认识 `writeback`，互不影响。

## 实现

- `core/src/source-writeback.ts`：`SourceWriteback` 负责手动写入、意图的投递（归属守卫、泳道、状态匹配、重试）、串行队列和记录；`source-writeback-store.ts` 在任务数据库里存回写记录（`source_writes`）、总结草稿（`source_reports`）和待投递的意图（`source_intents`）。
- 规则存在来源实例的配置里（`sources.json` 的 `writeback`，以及可选的 `writebackLanes`、`writebackOptions`），和设置一起保存。
- `TaskService.save` 是任务状态变化的唯一入口：`pending → running`、`running → review`、`→ done` 时，`SourceWriteback.journal` 给出的意图随状态变化一起写入，随后 `drain()` 在后台投递；启动时也 drain 一次。失败不影响任务本身的状态变化。
- 由规则发出、内容来自 Agent 的评论，发出前过 `channel-output.ts` 的 `redact` 和 `withoutMachinePaths`。总结带 `verification` 时作为单独一段附在后面。
- RPC：`sources.writeback`（记录和草稿）、`sources.writebackTransitions`、`sources.writebackTransition`、`sources.writebackComment`、`sources.writebackRetry`、`sources.saveWriteback`（可带 `lanes`、`options`，不带表示不变）、`sources.writebackPlan`（预览一步）、`sources.saveReport`（MCP 工具用）；通知 `sources.writebackChanged`。功能标记 `source-writeback`，泳道、演练和预览另有 `source-writeback-lanes`，独立类型规则另有 `source-writeback-per-type`；这些方法都不开放给手机。
- MCP 工具 `source_report` 只在会话属于带回写来源的任务或排查会话时出现，不需要用户批准（它只写 Antumi 自己的草稿）。
- 各插件的写法（用到的接口、状态怎么列、需要的 Token 权限、还没用真实账号确认的地方）写在 antumi-plugins 各插件的 README 和 DESIGN。

# 事项自动化

在设置的来源页面，「连接与同步」下方打开「事项自动化」，选择中枢 Agent 后保存。中枢就是一条普通会话：Agent、权限模式、提示词和项目由用户选，服务商和模型在「高级设置」里按需展开；「允许新建任务」决定它能否为事项新建任务。首次开启只记录当前查询中的问题，后续首次进入结果的问题才会自动创建排查会话。这里的“新”表示首次发现，也包括后来被指派给自己、第一次进入查询的旧问题。

默认每个来源实例每天最多新增 10 个自动会话，按 core 所在机器的本地日期计数；全部来源同时主动排查一个问题。原文准备、首次启动、回复以及迟到图片的补充均占用此名额。等待用户回答问题的会话让出自动名额，仍占用原有 Agent 进程名额；回答后排查接着进行。只有用户在会话里自己发消息或停止 Agent 才算接手，自动队列不再驱动该次排查。

自动启动使用设置里选的权限模式，未选时用 Agent 描述符的讨论模式（只读或规划）；选「全部放行」才允许绕过审批。来源原文仍作为不可信资料传入，说明文件只交出原文，不再写死排查步骤。首条消息是用户的提示词（没写就用 `DEFAULT_INVESTIGATION_PROMPT`：bug 确定根因后新建任务修，新功能只给结论，PR 只 review），后面接一段用户改不到的「和 Antumi 的配合」（`automaticInstructions`）：允许新建任务时怎么用 `source_task_create`，PR 类事项不建任务，事项的状态和评论交给回写规则，结束前用 `source_report` 写结论。自动阶段不找用户审批：Agent 请求的操作由 Antumi 代答。只读的操作自动放行，包括读文件、搜索、查网页、只读的 MCP 工具，以及不改动任何东西的命令（`ls`、`cat`、`rg`、`find`，`git log`、`git show` 这类 git 读取，`gh issue view`、`gh pr diff` 这类 gh 读取，管道或 `&&` 连起来的也行，按命令全文判断）。其余的选了「全部放行」才允许，否则拒绝，并让 Agent 换个做法或在总结里写明需要用户做什么。判断规则在 `core/src/command-rules.ts` 的 `readOnlyCommand`。提问照常通知，10 分钟没人回答就让它按合理假设继续。用户接手后，请求改回由用户审批。自动阶段不通过任务的无人值守预约启动，也不自动续跑被额度打断的会话。人工接手沿用原有会话操作。

## 新建任务

打开「允许新建任务」后，中枢判断需要改代码时调用 `source_task_create`（RPC `sources.createTask`）。它先用 `source_task_options` 查已登记项目、可用 Agent 和服务商，用 `source_task_catalog` 查模型和推理强度，再提交 `title`、`details`、`agent`、`repos[{path, reference?, startRef?}]`，以及可选的 `model`、`effort`、`modelProvider`、`dependsOn`。模型等为空表示执行 Agent 的默认值，不继承中枢的配置；权限不在参数里，任务按「预约运行的权限」（全局的无人值守模式）运行。这个工具不用用户审批，因为开关已经授权；没打开时 core 拒绝。

core 当场校验并建好任务，任何一步不过都把具体原因返回给中枢，让它修正后再调或写进结论：
- 来源仍开着自动排查和新建任务，排查会话还在进行；
- 来源不在演练模式，事项没完成，事项不是 PR（插件报告的类型是 `pull-request`：PR 在会话里 review，建任务会另开一个 PR）；
- 执行 Agent 和服务商可用，模型和推理强度可用；
- 项目已登记、不重复、第一个可写、目录存在，`startRef` 只能是 `HEAD`、`refs/heads/<分支>` 或 `refs/remotes/origin/<分支>`，依赖任务存在；
- 可写项目已配置并信任交付检查；
- 一个排查只建一个任务，一个事项只有一个任务（手动导入过的也算）。

不看事项归谁：要不要处理由用户的提示词决定；归属只约束回写规则。来源没有回写能力时，不知道事项的状态和类型，照样建。

任务、启动参数、依赖、来源快照和自动任务记录在同一事务中保存，建好就排队启动：执行 Agent 有空位时由 TaskService 准备独立分支和 worktree、初始化环境，再启动。任务建成后，评论只关注任务，排查会话停止关注；不中继评论，也不反复唤醒排查 Agent。core 在任务记录和任务之间退出时，那条记录标为失败，中枢可以再建。

任务回合结束后，core 校验任务分支及已提交状态，执行项目检查；失败最多反馈给原任务两次，第三次失败转人工。未配置检查、等待回答、进程退出、首次消息送达不明等情况停止自动推进并显示原因，不重复启动。检查期间代码变化会阻止交付。交付前再核实事项没完成、不在演练模式、配置没变：有 GitHub 远端的项目复用 PR 服务推送任务分支、创建 PR；其他项目不推送，提交留在任务分支上，总结的验证说明里写明分支。至少有一个项目有新提交才算交付，之后进入待验收，并按类型规则回写总结。PR 创建前不会发布提交验收的回写；不自动合并或验收。既有 PR 会被识别，重启不会重复建任务或重发首条指令。

用户继续任务的会话或操作任务后即接手，系统停止推进；任务和 worktree 保留。接手的是排查会话时，已建的任务照常推进。执行期间开启演练、关掉自动排查或新建任务会阻止交付。失败或中止不自动清理 worktree。

运行状态和关联任务、PR 链接显示在排查记录及原会话的来源区块。`source-hub-tasks` 标记这一版（中枢权限和提示词由用户定，`sources.createTask`）；新 RPC 不开放给手机。

## 发现与记录

core 的 `SourceInvestigationService` 接收 `SourceService` 成功同步的原始结果，不读取桌面端过滤后的列表。首次启用有成功结果就立即建立基线，否则等待第一次成功同步。已导入、已忽略和已有排查会话的问题同样记入已发现记录，但不进入自动队列。

配置、已发现编号及排查记录保存在现有 SQLite 数据库，与来源连接设置分开。一次事务写入新发现的编号和对应排队记录。来源身份包含 provider、instance、站点及账号绑定的摘要，不保存凭据原文；不同站点的相同编号分别处理。编号迁移时记录别名并再次查重。

普通重启保留基线。修改查询、重新登录、重新开启会重新建立基线；历史去重记录保留。关闭开关、关闭来源同步或更改查询会取消未开始的排队记录。项目、Agent、模型或提示词的调整只影响未领取的记录；已领取记录保留原配置以供恢复。删除会话不会删除去重记录，也不会自动重建。

当前每个来源结果最多保留 200 条，达到上限会提示收窄查询；本功能不会扩展插件的分页或补抓历史数据。

## 调度与恢复

成功同步、会话状态变化和名额释放触发调度，另有一分钟兜底检查。来源实例轮转领取记录，遵守既有全局及单 Agent 进程上限。新会话创建后计入当日数量；重试原会话不重复计数。达到每日上限的记录留在队列，次日继续。

排查记录 ID 同时作为预分配会话 ID，来源与自动标记随会话首次插入一起落库。首条指令使用稳定引用 `auto-investigate:<记录ID>`。恢复先对账 daemon，再判断已有会话、准备状态及投递回执，不能仅凭内存是否存在来重新创建。原配置及提示词跨重启保留；已提交正文的会话仅恢复未完成的图片下载，不重发首条指令。

准备阶段网络错误最多重试三次，间隔为 1、5、15 分钟。Agent 名额不足只等待，不消耗重试次数。配置、凭据或权限错误需修复对应原因。已提交的首条指令不自动重发；投递结果不明确的记录要求打开会话检查，保留启动日志和回执。对于可能还在执行的未确认投递，不开启下一条自动排查。

收件箱显示各条排查状态、今日数量及排队数量；来源设置和收件箱均可打开分页排查记录。安全可重试的失败记录提供重试，未开始的记录可以取消。失败记录或等待输入的会话沿用现有通知机制。

core 运行时不依赖桌面窗口。电脑休眠或 core 停止期间不执行，恢复后续跑。新能力标记为 `source-auto-investigation`；旧 core 不显示设置入口，旧客户端保存来源连接设置不会覆盖自动排查配置。
